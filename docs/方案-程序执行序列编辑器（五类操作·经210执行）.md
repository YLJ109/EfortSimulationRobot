# 方案 · 程序执行「序列编辑器」（五类操作 · 全部经控制器 210 执行）

> ★ 2026-09-29 增补：新增第 5 类操作「**放气**」（关真空 + 吹气脉冲 = 破真空脱件）。
> 起因是现场反馈：吸气 → 停止吸气之后**工件一直贴着不掉** —— 只关真空阀挡不住残余负压，
> 必须给一下正压才能脱开。位分配按铁律 3 新占 `40135.Bit3`（不复用 Bit2）。

> 2026-09-29 · 现场需求由用户下达
> 目标：在「程序执行」页提供一个像编辑器一样的序列编排器，用户自己把顺序排好，
> 一键执行 / 暂停 / 继续 / 停止，并可保存成本地文件、选择已保存文件执行。
> **只做这五类操作**：标记点、吸气、停止吸气、**放气**、等待。不引入第六类，不加其它按钮。

---

## 1. 范围（做什么 / 不做什么）

| | 内容 |
|---|---|
| **做** | 四类步骤的增 / 删 / 上下移；序列命名并**保存成本地文件**；**载入已保存文件**到编辑器；**选择文件执行**；**执行 / 暂停 / 继续 / 停止执行**；实时进度与当前步高亮；每一步的成败可见 |
| **不做** | 条件判断 / 循环 / 变量 / 子程序 / IO 自定义 / 速度曲线 / 分支跳转 / 多序列并行 —— 一律不加。**一次只跑一个序列** |
| **不改** | 现有的「示教器程序」「本地程序」「手动执行」三张卡的行为（除 io 步骤由"空转"变为**真的执行**，这是修 bug，不是加功能） |

---

## 2. 执行通道：为什么"经 210 执行"

控制器**同一时刻只能加载并运行一个程序**。本方案的每一类步骤都走
「上位机写目标/触发位 → 常驻程序 210 读取并执行」这条既有链路，**不加载新程序**：

| 步骤 | 上位机动作 | 控制器 210 侧动作 | 完成判据 |
|---|---|---|---|
| 标记点 | 写 40139~44 目标角 → 置 40135.Bit0 | `MJOINT(POINTJ(...), v50perc, fine, tool0)` | 40035.Bit0 置 1 |
| 吸气 | 置 40135.Bit1 | `io.DOut[N] := true`（**保持**） | 40035.Bit1 置 1 |
| 停止吸气 | 置 40135.Bit2 | `io.DOut[N] := false`（只关阀，不吹气） | 40035.Bit2 置 1 |
| **放气** | 置 40135.Bit3 | 关真空 + `io.DOut[M]` 吹气脉冲（程序内 `DWELL(0.40)`） | 40035.Bit3 置 1 |
| 等待 | 无（纯软件计时） | 不涉及 | 计时到点 |

**前置条件**：执行前必须确认 210 已加载并运行。用既有的
`modbus.rc_vacuum_prepare(210)` 做**幂等预检**（已在跑 → 立即返回；否则 伺服→停机→加载→运行）。

## 3. 数据格式（本地文件）

存放位置沿用既有可执行程序目录 `programs/`（`_program_dir()`），文件类型 `.json`：

```json
{
  "name": "取件-放件",
  "saved_at": "2026-09-29T18:30:00",
  "speed_pct": 5,
  "items": [
    { "point_id": 3,     "speed_pct": 5 },          /* ① 标记点 */
    { "op": "suck" },                                /* ② 吸气   */
    { "op": "wait",      "dwell_ms": 1500 },         /* ③ 等待   */
    { "point_id": 7 },                               /* ④ 标记点 */
    { "op": "release" }                              /* ⑤ 停止吸气 */
  ]
}
```

**为什么用这个格式**：`items` 与既有 `_load_disk` / `_steps_from` / `_candidates`
**完全兼容** —— 保存后的序列会立刻出现在「本地程序」列表、可被「手动执行」按文件名跑、
可被 `_candidates` 扫描到。**不另造一套格式**，避免同一件事两套真相。

`op` 取值严格限定 `suck | release | blow | wait`（XPL 解析器产出的 `op:"suck", on:false`
继续兼容，归一化为"停止吸气"）。

## 4. 后端设计

### 4.1 复用既有执行循环（不另写执行器）

`POST /api/control/run-file` 已有：按文件名解析 → 逐步执行 → 每步过围栏互锁 →
`motion.command(..., abort_check=_is_cancelled)` → 汇总 `steps[]` / `cancelled` / `run_id`。
**本方案在它上面补三件事**，而不是另起一个执行器：

1. **io 步骤真正执行**（当前是空转 + 注释"无真机吸气通道"，已过时）：
   `suck` → `rc_vacuum("suck")`；`release` → `rc_vacuum("release")`；
   `blow` → `rc_vacuum("blow")`（= 40135.Bit3 → 常驻程序关真空 + 吹气脉冲）；
   `wait` → 可暂停、可打断的计时。
   执行前按需 `rc_vacuum_prepare(service_program)` 保证 210 常驻。
2. **进度登记表** `_RUN_PROGRESS[run_id]`：循环每步更新
   `{index, total, name, step_name, phase, ok, error, paused}`，
   由 `GET /api/control/run-state` 读取 —— 前端据此画进度条与当前步高亮。
3. **暂停/继续**：`_RUN_PAUSE[run_id] = threading.Event`。
   - 步边界：进入下一步前若已暂停则阻塞（可被"停止执行"打断）；
   - 等待步：计时切片（50ms）推进，暂停时**冻结剩余时间**；
   - 点动/吸放步：**不中断**（控制器正在执行 MJOINT / 写 IO），暂停在**该步结束后**生效。
     这一点必须在界面上如实写明，不能让人以为"按下暂停机器人立刻停"（那是急停的语义）。

### 4.2 新增接口（全部 `require_control`）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/control/seq?name=` | 读本地序列文件 → `{ok, name, speed_pct, items}`（供编辑器载入） |
| `POST` | `/api/control/seq` | 保存序列到 `programs/<name>.json`（校验步骤 schema、大小上限、路径穿越） |
| `GET` | `/api/control/run-state` | 执行进度/暂停态快照（含 `run_id`、`total/index`、`paused`、`running`） |
| `POST` | `/api/control/run-pause` | 暂停当前序列（可带 `run_id`） |
| `POST` | `/api/control/run-resume` | 继续 |
| *(既有)* | `/api/control/run-file` | 执行序列（`filename` = 保存的文件名，或 `items` 直接跑编辑器缓冲） |
| *(既有)* | `/api/control/run-cancel` | **停止执行**（已接进 `motion.command` 的 abort_check，能打断飞行中的那一发） |

`run-file` 的请求体增加可选 `items`：不落盘也能直接跑编辑器里正在编的序列；
给了 `filename` 则忽略 `items`（以文件为准，避免"界面显示 A、实际跑 B"）。

### 4.3 互锁（安全）

- **一次只跑一个**：已有 `motion._exec_lock` + `_RUN_ACTIVE` 保证；再有新请求排队/拒绝。
- **序列执行期间拒绝手动点动/吸放**：`/control/jog/*`、`/control/vacuum` 在
  `_RUN_ACTIVE` 非空时拒绝，提示"有序列正在执行，请先「停止执行」"。
  理由：手动触发位与序列的触发位**共用同一个 40135 寄存器**，交错会互相清掉，
  产生谁也说不清的半截状态。
- **急停优先级最高**：`/control/estop` 不取 `_exec_lock`，任何时刻都能打断序列。
- 每一步仍走**原来的**全部护栏：真实下发双闸、AUTO 档位守卫、围栏互锁、
  轴锁（仅 J6）、速度硬下限 5%、报警守卫。

## 5. 前端设计（「程序执行」页新增一张卡：序列编辑）

```
┌ 序列编辑 ────────────────────────── [名称: 取件-放件] ─┐
│ 添加步骤:  [+ 标记点] [+ 吸气] [+ 停止吸气] [+ 等待]     │   ← 只有这四个
│ ─────────────────────────────────────────────────────  │
│ #1  标记点   取件位(12)    速度 5%      ▲ ▼ ✕          │
│ #2  吸气                   保持          ▲ ▼ ✕          │
│ #3  等待     1.5 s                       ▲ ▼ ✕          │
│ #4  停止吸气                             ▲ ▼ ✕          │
│ ─────────────────────────────────────────────────────  │
│ [保存到本地文件]  [载入…▾]  [清空]                       │
│ [▶ 执行] [⏸ 暂停] [▶ 继续] [■ 停止执行]                  │
│ 进度 ▓▓▓▓░░░░ 2/4 · 当前: 吸气 · 运行中                  │
└────────────────────────────────────────────────────────┘
```

- **标记点**：从已有点位下拉选择（`exec.points`，即"存储好的点"）。
- **等待**：秒数输入（0.1 ~ 3600）。
- 有未保存改动时「载入」「清空」需二次确认；执行中禁止编辑（避免"改着改着执行了别的"）。
- 载入来源 = 后端 `_candidates` 里 `group="local"` 且 `file_ext="json"` 的文件。
- 执行中每 500ms 轮询 `/control/run-state` 刷新进度与当前步高亮；结束后停轮询。

### 5.1 暂停语义（界面必须写明）

> 「暂停」在**当前步结束后**生效（等待步则立即冻结计时）。
> 想要机器人立刻停住，用**急停**。

## 6. 状态机

```
         ┌──────────┐  start   ┌──────────┐
         │  idle    │─────────▶│ running  │
         └──────────┘          └────┬─────┘
              ▲                     │ pause        ┌──────────┐
              │  finish/cancel/err  ├─────────────▶│ paused   │
              │                     │◀─────────────┤          │
              └─────────────────────┘   resume     └────┬─────┘
                                                          │ stop
                                                          ▼
                                                     cancelled
```
`running` / `paused` 期间：拒绝手动点动与吸放、拒绝新的执行请求；
**急停任何时刻可用**。

## 8. 实施顺序

1. 后端：`_steps_from` 兼容 `release`；`run-file` 实执行 io 步骤 + 210 预检；
   进度登记表 + `run-state`；`run-pause` / `run-resume`；`seq` 读写；互锁。
2. 后端：单元测试（步骤 schema 校验、暂停在等待步冻结计时、互锁拒绝、
   序列文件路径穿越防护）。
3. 前端：store 动作 + 「序列编辑」卡 + 轮询进度。
4. 构建 + 全量测试 + 真机验收（需控制器处于 AUTO）。
5. 文档：本方案 + 规范文档交叉引用；记忆落档。
