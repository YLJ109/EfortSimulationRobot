### 0.2 三个必须纠正的认知（否则改造方向会错）

1. **仿真不是在仿真**。`backend/app/services/kinematics.py:83 simulate_pose(t)` 是**与时间有关、与指令无关**的正弦扫掠（频率 0.07~0.23Hz、幅度为量程的 30%）。也就是说：**下发任何目标，模拟姿态都不受影响**。这直接导致前端不得不用 `setLocalDemo(true)` 把后端姿态流"掐掉"、改由前端自己一跳到位 —— 这是本次所有实时性问题的**总根源**。
2. **"实时更新"断在抑制开关上，不在读取侧**。`stores/robot.js:64` 的 `if (this.localDemo) return;` 一执行，`latestPose` 就冻结。而 `stores/exec.js` 有 **5 处** `setLocalDemo(true)`（257/304/353/440/576），只有 `leaveView()`（665）会置回 false。⇒ **只要在点位执行页做过任何下发，该页的关节/TCP 读数就永久停在那一刻**。
3. **执行页的 3D 只在指令回执时被"一跳写入"**（`stores/exec.js` 的 7 处 `applyRobotPose`），从不连续跟随实时姿态。所以跑程序时，除了残影预演的下一步，看不到机器人真的在动。

## 3. 核心设计：姿态权威模型（本方案的地基）

### 3.1 设计目标

1. **遥测永远不被抑制** —— 任何页面、任何时刻，读数都是实时的。
2. **只有一个写者** —— 前端每个视图最多写 3D 一次，来源明确、互斥。
3. **"离线演示"是唯一被允许接管姿态的特例**，且必须是显式、可关闭、可解释的。
4. **仿真要真的是仿真** —— 下发目标必须改变模拟姿态（否则遥测在模拟模式下毫无意义，第 1 条就是空话）。

### 3.2 数据模型（`stores/robot.js` 重构）

```js
state: () => ({
  // ── 遥测（后端唯一真值，永不抑制）────────────────────────────
  telemetry: {
    q: [0,0,0,0,0,0],       // 关节角（度）
    tcp: { x:0, y:0, z:0 },
    simulated: false,       // 该帧是否为模拟数据
    cmd: null,              // ★ 新增：后端最近一次指令目标（motion.last_target）
    cmdAt: 0,               // ★ 新增：该指令的时间戳
    at: 0,                  // 本帧到达时刻
  },
  // ── 离线演示（唯一允许接管姿态的特例）────────────────────────
  demo: { on: false, q: [0,0,0,0,0,0] },
  // ── 元数据 ─────────────────────────────────────────────────
  meta: null, limits: [...], connected: false, activeView: "live",
})
```

`applyPose(p)` 重写（**删掉 `if (localDemo) return`**）：

```js
applyPose(p) {
  this.simulated = !!p.simulated;
  this.connected = true;
  this.telemetry = {
    q: [p.j1, p.j2, p.j3, p.j4, p.j5, p.j6],
    tcp: p.tcp ? { x: p.tcp.x, y: p.tcp.y, z: p.tcp.z } : this.telemetry.tcp,
    simulated: !!p.simulated,
    cmd: p.cmd || null,
    cmdAt: Number(p.cmd_at) || 0,
    at: Date.now(),
  };
}
```

**显示姿态（唯一入口，所有视图都必须用它）**：

```js
getters: {
  /**
   * 3D 应当显示的姿态。★ 全站唯一的"显示姿态"判据 ——
   * 任何视图都不得自己算出第二个来源（这正是改造前三页不一致的成因）。
   */
  displayQ(s) {
    if (s.demo.on) return s.demo.q;                    // ① 离线演示优先（显式开启）
    if (s.telemetry.simulated && s.telemetry.cmd) {    // ② 模拟模式下，指令即位置
      return s.telemetry.cmd;                          //    （见 §4-C：真机模式不吃这条）
    }
    return s.telemetry.q;                              // ③ 默认：遥测真值
  },
  displayTcp(s) {
    if (s.demo.on) return s.demo.tcp || s.telemetry.tcp;
    if (s.telemetry.simulated && s.telemetry.cmd) return s.telemetry.cmdTcp || s.telemetry.tcp;
    return s.telemetry.tcp;
  },
  /** 读数卡用：始终是遥测（"机器人现在在哪"就是遥测，不是显示姿态）。 */
  readoutQ: (s) => s.telemetry.q,
  readoutTcp: (s) => s.telemetry.tcp,
}
```

> **为什么读数用 `telemetry` 而不是 `displayQ`？**
> 读数回答的是"机器人现在在哪"。离线演示/指令回执都是**前端造的像**，不是机器人的位置。
> 在真机模式下二者恒等；在模拟模式下，`cmd` 就是模拟机器人被命令去的位置（因为 §4-C 让仿真真的走过去了），所以也一致。

### 3.3 显示策略矩阵（改造后）

| 页面 | 3D 姿态 | 读数卡 | 残影 | 说明 |
|---|---|---|---|---|
| 真实监控 | `displayQ`（在线）／跳舞（离线演示开启时） | `readoutQ` | — | 行为不变 |
| 点位执行 | **`displayQ`（连续跟随，逐帧）** | `readoutQ` | 示教目标 | ★ 本次核心改动：真机模型跟随机器人，残影负责"我要去哪" |
| 程序执行 | **`displayQ`（连续跟随，逐帧）** | `readoutQ` | 下一步目标 | ★ 跑程序时能看着机器人动 |
| 模拟仿真 | `robot.simQ`（本地教学模型，不动） | 无 | — | 保持隔离：这是"教学/预演"沙盘，不是遥测 |
| 录制回放 | 回放帧 | 无 | — | 不变 |

**"连续跟随"的实现方式**：不再由各视图自己调 `applyRobotPose`，而是由**唯一的一处**驱动：

```js
// App.vue 的 RAF 主循环内（已有 requestAnimationFrame(loop)，:268-272）
function loop() {
  ...
  // ★ 全站唯一的姿态下发点：3D 永远跟着 displayQ 走。
  //   各视图只负责"决定 displayQ 是什么来源"（见 stores/robot.js 的 getter），
  //   不负责调用 applyRobotPose —— 这样就不可能有两个写者。
  applyRobotPose(robot.displayQ);
  manager.renderFrame(now);
  requestAnimationFrame(loop);
}
```

`SimMonitor` 与 `recording` 的独立模型改为**写入 store 的一个 `override` 字段**而不是直接调 `applyRobotPose`：

```js
// stores/robot.js
override: null,   // { q:[...6], tcp:{...}, owner:"sim"|"rec" }
```
`displayQ` 的优先级变为：`override`（仅当其 owner 是当前 activeView）> `demo` > `telemetry`。
`manager` 侧不再暴露给业务代码 —— `applyRobotPose` 只在 `App.vue` 与 `manager` 内部使用，其余一律走 store。

### 3.4 离线跳舞的收敛

改造后 `localDemo` 这个"隐性全局抑制开关"被 `demo.on` 取代，并且：

- **只有** `RealMonitor` 能设 `demo.on`（它是"离线演示"这个功能的 owner）。
- `exec.leaveView()` **删掉** `useRobotStore().setLocalDemo(false)`（P1-10）。
- `RealMonitor.onBeforeUnmount` 里的 `setLocalDemo(false)` 也删（v-show 下不会触发，留着只会误导）。
- `demo.on=true` 期间 `readoutQ` **仍然显示遥测**（离线时遥测是合成轨迹，但至少是"后端认为的姿态"）；如产品上希望离线时读数也显示跳舞姿态，则改为 `readoutQ` 在 `demo.on` 时回落到 `demo.q` —— **这一条需要产品确认，默认取前者（读数=遥测）**。

### 3.5 生命周期统一约定（写进项目规范）

### C. 让仿真真的是仿真（根因，也是 A 的前提）

现状 `simulate_pose(t)` 与指令无关。改造为**有状态仿真器**：

```python
# backend/app/services/simrobot.py（新增）
class SimRobot:
    """有状态的模拟机器人：把 motion.last_target 当作目标，按速度限制走过去。
    ★ 这是"仿真"二字的实际含义：下发一个目标，模拟姿态必须真的走过去。
      改造前它是与时间有关、与指令无关的正弦扫掠 —— 下发目标不改变任何东西，
      这直接导致前端不得不把遥测掐掉（setLocalDemo），是"三页不一致"的总根源。
    """
    def __init__(self): self.q = [0.0]*6; self.target = None; self.dps = 30.0; self.idle = True
    def command(self, q, speed_pct):  # 由 motion.command() 调用
        self.target = list(q); self.dps = max(1.0, 90.0 * speed_pct / 100.0); self.idle = False
    def step(self, dt, t):
        if self.idle:  # 从未收到指令：保持原有的缓慢演示扫掠（保留既有观感）
            return simulate_pose(t), True          # True = 本帧为"演示像"，非指令像
        moved = False
        for i in range(6):
            d = self.target[i] - self.q[i]
            mx = self.dps * dt
            if abs(d) <= mx: self.q[i] = self.target[i]
            else: self.q[i] += mx * (1 if d > 0 else -1); moved = True
        if not moved: self.idle = True             # 到位后回到演示扫掠
        return [round(v,3) for v in self.q], False
```

- `collector._loop` 的模拟分支改调 `simrobot.step(dt, t)`。
- `motion.command()` 在 sim 分支调 `simrobot.command(...)`。
- 遥测 payload 增加 `cmd` / `cmd_at` / `idle`（前端 §3.2 用到）。
- **保持 `simulate=always` 的锁定语义**（P1-4 一并修）。

> 为什么这样能同时解决"模拟下读数无意义"和"真机下要实时"：
> 真机模式 ⇒ `telemetry.q` 是 Modbus 真实读回，天然实时；
> 模拟模式 ⇒ `telemetry.q` 是"被指令驱动走过去"的姿态，**也是**有意义的当前位置。
> 两种模式下前端逻辑完全一致 —— 再没有 `setLocalDemo` 这种分叉。
