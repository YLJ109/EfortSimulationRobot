# 示教器双模式与运动坐标系适配方案

> 对应需求原文：「示教器有两种机器人控制模式一个是机器人另一个是示教器控制，你可以去官网参考，
> 机器人的整体的移动就不一样了，要适配适应」
>
> 本文只写方案，**不改代码**。实施按第 12 节分期进行。

---

## 1. 结论先说

「机器人的整体移动不一样」在官方语义里其实是**两件独立的事**，必须拆成两层做，
混成一层的话后面一定会返工：

| 层 | 官方叫法 | 决定什么 | 例 |
|---|---|---|---|
| **L1 运行模式** | 模式旋钮：`T1` / `T2` / `AUTO(回放)` / `REMOTE(远程)` | **谁在控制**机器人（示教器 or 控制器自己跑程序） | AUTO 下点动按钮直接无效 |
| **L2 运动坐标系** | 状态栏坐标系：`关节` → `机器人` → `工具` → `用户` | **往哪个方向走**、步长单位是什么 | 按「1+」在关节系是 J1 转，在机器系是沿 X 平移 |

用户说的"一个是机器人另一个是示教器控制"，最贴近的官方对应物是 **L2 里的
`机器人坐标系`**（官网原文：「点击状态栏"关节"，将机器人运动坐标系选择为"机器人"」）——
因为只有它才会让"整体移动"看起来完全不同：关节系下是各轴各自转，机器系下是 TCP 沿直线走。

**但 L1 也必须做**，理由见 §3：真实示教器在 AUTO 档是**不允许点动**的，我们现在没有这一层门控。

> ⚠️ 待确认项见 §13。若用户本意只是 L2，L1 也可以只做"状态显示 + 拒绝点动"，工作量很小，不浪费。

## 2. 官方语义对照（依据）

来源：
- EFORT 机器人学院《关节坐标系下操作机器人》 `/college/detail/473.html`
- EFORT 机器人学院《机器人坐标系下操作机器人》 `/college/detail/477.html`
- EFORT 机器人学院《用户坐标系下操作机器人》 `/college/detail/485.html`
- 《ER20-1700 Quick Operation Manual》 4.3 Jogging（英文版流程与坐标系切换顺序）
- 《ER 系列机器人操作手册》 5.5 开始点动操作（坐标系切换顺序、状态栏显示）

### 2.1 运动坐标系（L2）

| 坐标系 | 原点 / 轴向 | 轴按钮含义 | 步长单位 | 备注 |
|---|---|---|---|---|
| **关节** | 各关节自身 | `1±`~`6±` = J1~J6 正/反 | **度 (deg)** | 各关节独立运动，适合大范围移动 |
| **机器人** | **机器人底座中心**；Z 竖直向上；X 由**底座航插对向**确定；Y 右手定则 | `1±`=X，`2±`=Y，`3±`=Z，`4±`=A，`5±`=B，`6±`=C | **mm**（A/B/C 为度） | A=绕Z，B=绕Y，C=绕X，右手螺旋 |
| **工具** | 当前激活的 **TCP** | 同机器人系（沿工具自身 X/Y/Z + 绕 A/B/C） | mm / 度 | 用于"贴着工具方向"进给 |
| **用户** | 用户自定义，一般取在**工件**上 | 同机器人系 | mm / 度 | `wobj0` = **机器人坐标系**（默认）；`wobj1`~`wobj5` 可自定义 |

切换方式与顺序（官网 + 手册一致）：
> 点击状态栏坐标系按键，或按示教器面板上的坐标系切换键，
> 顺序依次为 **关节 → 机器人 → 工具 → 用户**，切换结果显示在状态栏。

### 2.2 点动方式与速度（L3）

- **连续点动**：按住 `+`/`-` 持续走，松开立即停。
- **增量点动（步进模式）**：绿色快捷键开启，每次按键走一个**步长**，步长可设、**单位随坐标系变化**
  （关节系为度，直角系为毫米）。再按一次绿色键取消。
- **慢速模式**：黄色快捷键，**TCP 速度放慢 10 倍**，用于接近目标点时防撞。
- **速度倍率**：手动低速（T1）最高 **20%**；手动高速（T2）与自动模式最高 **100%**，
  且需按下电柜的自动确认按钮。
- **T1 下 TCP 速度上限：50 mm/s**（慢速模式下 5 mm/s）。
- 使能：**三段式手压开关**，保持在**中间档位**时伺服上电（抱闸打开、电机通电）；
  轻按 = 伺服使能档，**重按到底 = 急停**。
- 合成动作：工件/用户坐标系下同时按两个以上轴操作键 → 合成运动；
  同轴正反两键同时按 → 该轴不动作。

### 2.3 三种奇异点（直角坐标系点动必须处理）

| 奇异点 | 成因（官方原文） | 后果 |
|---|---|---|
| **腕部** | J5 位于 0° 时，J4 与 J6 轴线重合 | 直线轨迹规划失效 |
| **肩部** | 腕部轴中心与 J1 底座中心共线 | 同上 |
| **肘部** | J2、J3 轴中心与腕部轴中心共线 | 同上 |

官方处置方式：
> 「在使用机器人/用户坐标系操作时，如果机器人位于奇异点附近，会触发报警，
> **需要切换成关节坐标系**，才能继续移动机器人。」

→ 所以我们的直角点动必须能**提前预警并把用户引导回关节系**，而不是下发后报错。

### 3.1 一个必须承认的现实约束

我们**现在读不到控制器的当前模式**（`config/robot.yaml > modbus` 只映射了关节角寄存器
10~21，没有模式/使能寄存器），而且写寄存器地址本身还是 `TODO`（真实下发未启用）。
所以 L1 只能这样做，**不做假实现**：

1. 前端在 `Position` 页显式声明「当前处于 T1 手动」——它是一个**用户确认项**，不是一个读数；
2. 后端把 `motion.mode_claim` 当作**配置**而非实测，用于**拒绝**点动（声明为 AUTO 时禁止），
   **绝不用它去放行任何原本被拦的操作**（fail-closed）；
3. 真正读取控制器模式寄存器，与 `write_base_addr` / `estop_addr` 一起作为**同一批**真机
   联调 TODO，在 §12 P5 单独处理。

这样 L1 是"只拦不放"的安全层，即使声明错了也不会造成危险，只是可能拦得过多。

## 4. 设计总览：三层 + 一个抽象

```
                    ┌─────────────────────────────────────────┐
   操作请求  ─────► │ L1 运行模式门控  T1 / T2 / AUTO / REMOTE │  ← 只拦不放
                    │    + 伺服使能(三段开关) + 急停            │
                    └───────────────────┬─────────────────────┘
                                        │ 通过
                                        ▼
                    ┌─────────────────────────────────────────┐
                    │ L2 运动坐标系  joint|base|tool|user      │
                    │   求解：Δ关节角 / Δ位姿 + IK → q_goal    │
                    └───────────────────┬─────────────────────┘
                                        │ q_goal
                                        ▼
                    ┌─────────────────────────────────────────┐
                    │ L3 运动方式  连续 / 增量步进 / 慢速       │
                    │   + 速度换算与关节速度夹紧               │
                    └───────────────────┬─────────────────────┘
                                        │
                    ┌───────────────────▼─────────────────────┐
                    │ 既有安全链（不动）：限位 → 围栏互锁 →     │
                    │ 急停 → motion.command() → 双确认真实下发 │
                    └─────────────────────────────────────────┘
```

**核心抽象：坐标系统一成一个 `frame` 描述符**，避免为每个坐标系写一套分支：

```python
Frame = {
  "id": "joint" | "base" | "tool" | "user",
  "user_id": "wobj0".."wobj5",     # 仅 user
  "kind": "joint" | "cartesian",
  "axes": ["J1".."J6"] | ["X","Y","Z","A","B","C"],
  "unit": "deg" | "mm",            # 平移量单位；旋转量恒为 deg
  "rot_unit": "deg"
}
```

其中 **`机器人坐标系 ≡ wobj0`**（官方明文），所以 `base` 不需要单独实现，
它就是"原点/方向取默认值的 user frame"。这一条能省掉一整份代码。

## 5. L1 运行模式与使能：详细设计

### 5.1 模式档位

| 档位 | 允许点动 | 允许程序运行 | 速度上限 |
|---|---|---|---|
| `T1`（手动低速，示教） | ✅ | ❌ | **20%**（TCP ≤ 50 mm/s） |
| `T2`（手动高速） | ✅ | ❌ | 100%（需电柜自动确认） |
| `AUTO`（回放/自动） | ❌ | ✅ | 100% |
| `REMOTE`（远程） | ❌ | 由外部（PLC）触发 | — |

### 5.2 后端落地

```yaml
# config/robot.yaml 新增
motion:
  mode_claim: "T1"        # T1|T2|AUTO|REMOTE —— ★ 这是"声明"不是"读数"，见 §3.1
  mode_source: "claim"    # claim | modbus（modbus 待真机联调后再切）
  jog:
    max_speed_dps: 30     # 已有：关节系角速度上限
    max_speed_mmps: 50    # 新增：直角系 T1 下 TCP 线速度上限（官方 50 mm/s）
    slow_factor: 10       # 新增：慢速模式 = 速度 /10（官方）
    slow_speed_factor: 0.1
    step_mm: [0.1, 1, 5, 10]   # 新增：直角系步长档位（mm）
    step_angles: [0.1, 1, 5, 10]  # 已有：关节系步长档位（deg）
    singularity_warn_deg: 5.0     # 新增：|J5| < 该值 → 腕部奇异预警
    singularity_block_deg: 1.0    # 新增：|J5| < 该值 → 直角点动拒绝
    shoulder_warn_mm: 30.0        # 新增：腕心到 J1 轴线距离预警
    manipulability_min: 0.02      # 新增：可操作度下限（通用预警）
```

**门控逻辑（只拦不放）**：
`jog.start/step()` 入口在既有 `_block_reason()` 里**追加两问**：

1. `mode_claim` 不在 `{T1, T2}` → 拒绝，原因："当前为自动/远程模式，禁止手动点动"；
2. 请求速度按模式夹紧：`T1` 下 `min(请求速度, 20% 上限)`。

`_block_reason()` 现有的三问（急停 / 围栏互锁 / 限位）**一行不动**，顺序放在新逻辑之前，
保证安全链优先级不被稀释。

### 5.3 伺服使能（三段开关）

现在没有"伺服使能"状态：只要拿到令牌就能点动。真实示教器必须**按住使能开关**。

设计为**前端保持信号**（复用已有的看门狗机制，不新增线程）：

- 前端按住"使能"按钮（或长按点动区）时，`jog/keepalive` 里多带 `enabled: true`；
- 后端在 `_state_locked()` 里暴露 `servo_enabled: bool`，由最近一次 keepalive 是否带
  `enabled` 推出，超时（= `watchdog_ms`）自动落回 `false`；
- `jog.start()` 要求 `servo_enabled == true`，否则拒绝：
  "请先按住伺服使能（三段开关中间档）"。

★ 复用看门狗的理由：**"松手即停"和"松使能即停"在时序上是同一件事**，
共用一条超时链就不会出现"使能还开着但点动已经停了"的矛盾状态。

> 这一条同时解决了另一个隐患：现在只要按下点动就会一直走，松手靠前端发 stop，
> 前端崩溃/断网时靠 1500ms 看门狗。加上使能语义后，安全边界更贴近真机。

## 6. L2 运动坐标系：详细设计

### 6.1 求解链（joint 与 cartesian 唯一分叉点）

```python
def solve_jog(frame, axis, dir, amount, q_cur, ctx) -> list[float]:
    if frame.kind == "joint":
        # 现有行为，一行不改
        q = q_cur[:]; q[axis-1] += dir * amount
        return clamp_limits(q)

    # ---- cartesian ----
    T_cur = fk_matrix(q_cur)              # 法兰位姿（机器人坐标系）
    R, u  = frame_rotation(frame, ctx)    # frame 在机器人系下的姿态 R 与原点 u
    delta = transform_in(frame, axis, dir, amount)
    #   base/wobj : 左乘 → T_goal = delta · T_cur        （在世界/基座系里增量）
    #   tool      : 右乘 → T_goal = T_cur · delta        （沿工具自身轴增量）
    T_goal = delta @ T_cur if frame.pre_multiply else T_cur @ delta
    res = ikine(T_goal, q0=q_cur, joint_limits=limits)
    if not res["ok"]:
        raise JogError("逆解失败：目标位姿超出可达空间或接近奇异点")
    return clamp_limits(res["joints"])
```

要点：

1. **`base` 与 `user` 共用一条代码路径**，只差 `frame_rotation()` 返回的 `(R, u)`。
2. **`tool` 是右乘**（沿自身轴），`base/user` 是**左乘**（沿参考系轴）——搞反了症状是
   "方向不对但看起来能动"，最难发现，必须有 headless 钉子（见 §11）。
3. **IK 初值必须用当前关节角**（`q0=q_cur`），否则会跳到另一个解（如肘上/肘下翻转），
   表现为机器人突然大幅度甩臂。
4. IK 若返回 `pos_err` 偏大，**必须拒绝而不是"尽力而为"**——宁可报"不可达"。

### 6.2 各坐标系的 `frame_rotation()`

**`base`（≡ `wobj0`）**：
```
u = (0,0,0)
R = base_frame_R          # 见下方 ★
```
★ **基座 X 向由"底座航插对向"决定，我们从配置里推不出来**，必须实测。
新增配置：
```yaml
frames:
  base:
    # 机器人坐标系：Z 向上，X 由底座航插对向确定。
    # 以下三项需**真机实测**后填写（当前为厂商通用构型假设，未核对）。
    x_axis_yaw_deg: 0.0    # X 轴在水平面内的偏航（相对 DH 基座系）
    z_sign: 1              # Z 向上为 +1
    verified: false        # ★ false 时前端显示"基座系未标定，方向仅供参考"
```
`verified: false` 时**不禁止**点动（否则真机联调前完全没法用），但在 UI 上明确标注。

**`tool`**：
```
T_flange = fk_matrix(q_cur)
t_tcp    = 当前激活工具偏移 (x,y,z)   # 复用已有 points/programs 的 tcp 字段
T_tool   = T_flange · Trans(t_tcp)    # 工具系原点 = TCP
u, R     = T_tool 的位置与姿态
```
★ 当前项目里 TCP **只有位置、没有姿态**（`teachTcp` 是 `{x,y,z}`）。这意味着工具系与法兰系
**姿态相同**。要支持真正的"工具姿态"，需要给工具加一个 `rpy` 字段——本期**不做**，
在方案里登记为后续项（§12 P4），并在 UI 上写明"当前工具系姿态 = 法兰姿态"。

**`user`（`wobj1`~`wobj5`）**：新增配置 + 三点法标定：
```yaml
frames:
  wobj0: { ... base ... }        # wobj0 即机器人坐标系
  wobj1: { x: 0, y: 0, z: 0, rx: 0, ry: 0, rz: 0, name: "工件A", verified: false }
  # ... 最多 wobj5
```
- 直接给 6 维位姿（`x,y,z,rx,ry,rz`）即可，UI 提供"用当前 TCP 位姿填充"按钮（示教式标定）；
- 三点法（原点 + X 向点 + XY 平面点）是**可选增强**，放 P4。

### 6.3 轴按钮映射（官方）

| frame | `axis=1` | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| joint | J1 | J2 | J3 | J4 | J5 | J6 |
| base / tool / user | X | Y | Z | A(绕Z) | B(绕Y) | C(绕X) |

轴 4/5/6 在直角系下是**旋转**（单位 deg），1/2/3 是**平移**（单位 mm）。
→ 所以 `unit` 是**按轴**决定的，不是按坐标系。这一点必须在 `frame` 描述符里体现：
```python
"unit_of_axis": lambda a: "deg" if a >= 4 or kind == "joint" else "mm"
```

前后端都要按这个映射显示单位，否则会出现"步长 1 mm"实际是"1 度"的静默错误。

## 7. L3 运动方式：详细设计

### 7.1 三种方式

| 方式 | 触发 | 关节系 | 直角系 |
|---|---|---|---|
| 连续 | 按住 `+`/`-` | `q_i += dir · ω · dt` | `TCP += dir · v · dt`（每 tick 求一次 IK） |
| 增量（步进） | 单击 `+`/`-` | `q_i += dir · step_deg` | `TCP += dir · step_mm`（一次 IK） |
| 慢速 | 慢速开关 | ω /= 10 | v /= 10 |

### 7.2 ★ 直角连续点动的速度换算与关节夹紧（最容易漏的一条）

直角系给的是 **TCP 线速度 v (mm/s)**，但 `motion.command()` 最终下发的是**关节角**。
不同位姿下 `Δq = J⁻¹·Δp` 的放大倍数差几十倍：靠近奇异点时 1mm 可能需要几十度关节运动。

所以每一 tick 必须：

```python
dq = J⁻¹ · Δp                      # 期望关节增量
scale = 1.0
for i in 1..6:
    need = abs(dq[i]) / (tick_ms/1000)
    if need > max_speed_dps:       # 单轴角速度上限
        scale = min(scale, max_speed_dps / need)
dq *= scale                        # 整体等比缩小 → 不改变运动方向，只降速
```

**为什么不直接拒绝**：拒绝会让用户觉得"走到某处就点不动了"；等比缩小则表现为
"越靠近奇异点走得越慢"，正好符合真机行为，并且**给出提示**：
`"接近奇异点，已自动降速至 32%"`。

这个 scale 也要回传给前端显示 —— 这是现场判断"我是不是快撞奇异点了"的最直观信号。

### 7.3 连续点动的求解频率

`tick_ms = 100`（10Hz）时，直角系每 tick 做一次 `ikine`（`max_iter=300`，含数值雅可比
6×6差分 = 每次 7 次 FK）。10Hz 下 CPU 压力可接受，但要**加一个保险**：

- `ikine` 用 `max_iter=60` 的"点动模式"预算（当前位姿离目标只有几 mm，几十次迭代足够）；
- 若某 tick 的 `ikine` 耗时 > `tick_ms`，**丢弃该 tick 而不是排队**（点动是"实时"语义，
  排队的旧指令下发出去会造成"松手还在动"）。

## 9. 前端设计

### 9.1 控件（`PointExecView.vue` 点动区）

```
┌ 点动 ─────────────────────────────────────────────────────┐
│ 坐标系 [关节 ▾]   运行模式 [T1 手动 ▾]   慢速 [ ]  使能 [⊙]│
│ ─────────────────────────────────────────────────────────│
│ 关节系面板：  J1 J2 J3 J4 J5 J6   步长 [0.1|1|5|10] °      │
```

- 轴按钮**跟着坐标系换标签**，不是固定 J1~J6（这是"适配适应"最直观的体现）；
- 步长**单位跟着坐标系换**；
- 奇异点/降速用**黄色提示条**，不是弹窗（点动过程中弹窗会打断操作）；
- 基座/用户坐标系 `verified: false` 时，坐标系名后加 `*`，hover 提示"方向未标定，仅供参考"。

### 9.2 3D 坐标系可视化（新文件 `three/frames.js`）

在机器人底座处画当前坐标系的三轴箭头：**X 红 / Y 绿 / Z 蓝**（与 `three/` 现有配色一致），
选中轴**加粗高亮**，并画一个步长刻度的短线段表示"这一步要走多远"。

★★ **必须注意的坑：three.js 场景是 Y-up，机器人基座系是 Z-up。**
箭头**不能**直接按场景坐标画，必须先做一次轴映射（基座系 `(x,y,z)` → 场景 `(x, z, y)`
且符号需按 `z_sign` 校正）。这个映射错了的症状是"箭头指向和实际运动方向不符"，
而模型本身完全正常 —— 属于典型的"看不见的错"。**用 headless 断言钉死**（§11）。

`frames.js` 只做纯几何计算 + 导出 `frameAxes(frame, ctx)` 返回三个向量，
用 `tools/verify_frames.mjs` 在 node 里断言，不在浏览器里试。

### 9.3 store 变更（`stores/exec.js`）

新增 state：`frame`、`userFrame`、`slow`、`modeClaim`、`servoHeld`、
`stepByFrame`（`{ deg: [...], mm: [...] }`）、`singularity`。
新增 getter：`axisNames`、`axisUnit`、`stepList`、`jogAvailable`（综合模式 + 使能 + 权限）。
★ getter 统一取名 `jog*` 前缀，避免与已有 `Icon` 对象键、函数形参撞名
（历史上 `announcer.js` 就因为导出名 `cfg`/`history` 触发过 `check_imports` 假阳性）。

## 11. 验收标准

### 11.1 后端 pytest（新增 `backend/tests/test_jog_frames.py`）

必须覆盖（每条都是会真实踩到的坑）：

1. **向后兼容**：不带 `frame` 的 `/jog/start`、`/jog/step` 行为与结果字段与现在一致；
2. **base 系**：沿 `Z+` 增量 10mm（`frame=base, axis=3`）后，`forward_kinematics(q_new).tcp`
   的 Z 比原来**增加约 10mm**（误差 < 0.5mm）；沿 `X+` 同理验 X；
3. **tool 系 vs base 系可区分**：把 J1 转 90° 后，`frame=tool, axis=3` 与 `frame=base, axis=3`
   产生**不同**的关节角（若两者恒等，说明 left/right multiply 写反了）；
4. **单位按轴**：直角系 `axis=1..3` 的 `unit` 是 `mm`，`axis=4..6` 是 `deg`；joint 系恒为 `deg`；
5. **限位夹紧**：把机器人摆在 J6 接近 `360°` 处，直角点动后 `q6` 不超过限位；
6. **腕部奇异点**：J5 置 0（±0.5°）后 `frame=base` 点动 → 被拒绝且原因含"奇异"；
   而同一姿态下 `frame=joint` **仍然允许**（官方行为：切关节系才能动）；
7. **模式门控**：`mode_claim=AUTO` 时所有点动被拒绝；`T1` 下速度被夹到 ≤20%；
8. **伺服使能**：未声明 `servo=true` 时 `start` 被拒绝；keepalive 带 `enabled` 后放行；
   超时（超过 `watchdog_ms`）后 `servo_enabled` 自动落回 `false` 且点动已停；
9. **慢速模式**：`slow=true` 时下发速度 = 正常值的 1/10；
10. **用户坐标系**：`user_frame` 未定义 → 400；定义后沿其 `X+` 移动，在机器人系里的位移
    方向与 `wobj` 的 `rz` 一致（转 90° 后 X 位移映射到机器人系 Y）；
11. **IK 不可达**：目标 TCP 设到 2000mm（超 `reach_mm` 712）→ 拒绝，且**没有**下发；
12. **围栏互锁仍然优先**：围栏 danger 时即使 frame/模式都对，也必须拒绝（防新逻辑绕过旧互锁）；
13. **全局状态复位**：`autouse` fixture 里复位 `jog`、`motion.mode_claim`、`servo_enabled`
    （模块级单例在测试间会串味，历史踩过）。

确定性技巧（沿用 `test_jog.py` 的既有做法）：先 `POST /control/move {joints:[0]*6}`
把 `motion.last_target` 钉在原点，再点动，结果即可精确预测，不受模拟采集漂移影响。

### 11.2 前端 headless（新增 `tools/verify_frames.mjs`，挂进 `npm run verify`）

1. `joint` 系的轴名恒为 `J1..J6`，`base/tool/user` 恒为 `X,Y,Z,A,B,C`；
2. `unitOfAxis(frame, axis)`：直角系 1~3 → `mm`，4~6 → `deg`；关节系全 `deg`；
3. **左右乘方向钉子**：构造一个人为的 `frame_R`，断言 `solveJogDelta` 对
   `base`（左乘）与 `tool`（右乘）产生**不同**的 4×4 结果（反证：若实现把两者写成同一分支，
   这里必然失败）；
4. **Y-up ↔ Z-up 映射钉子**：给定基座系向量 `(1,0,0)/(0,1,0)/(0,0,1)`，
   断言映射到场景后分别落在预期轴上、长度不变、且两两正交（行列式为 +1，不含镜像）；
5. 基座 `z_sign = -1`（吊装）时，映射结果 Z 取反，且仍为右手系；
6. 步长档位：切到直角系后默认步长取 `step_mm[1] = 1`，切回关节系取 `step_angles[1] = 1`；
7. 奇异点分级：给定的 `(q5, 腕心距, 可操作度)` 组合映射到 `ok/warn/block` 的**边界值**
   逐个钉死（含恰好等于阈值的临界点）。

### 11.3 手工验收（真机，不可省）

- [ ] 关节系点动方向与真机示教器**逐一比对 J1~J6**（含 `axis_sign` 生效后）；
- [ ] 机器人系 `1±` 是否真的是 X 平移（**核对航插对向**，填 `frames.base.x_axis_yaw_deg`）；
- [ ] 工具系沿 Z 进给是否贴着工具方向；
- [ ] 慢速模式实测是否 ≈ 1/10 速度；
- [ ] T1 下 TCP 速度是否 ≤ 50 mm/s（目测 + 计时量位移）；
- [ ] 把机器人开到 J5≈0，确认直角点动被拒且提示"切回关节系"。
