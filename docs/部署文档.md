# EFORT Web Monitoring 部署运维文档

> 适用版本：`0.3.0`（含阶段 3 运维增强 + 阶段 4 企业级加固）
> 适用对象：本机演示、车间看板、以及未来连接真机的生产运行。

---

## 1. 服务组成与端口

| 服务 | 端口 | 说明 | 必须？ |
|---|---|---|---|
| 后端 API + WS | `8000` | FastAPI，同时托管前端构建产物 `frontend/dist` | 是 |
| 视觉/相机服务 | `8100` | 海康 MVS 抓帧 + YOLO 检测 | 否（无相机可不开） |
| 前端开发服务器 | Vite 默认 5173 | 仅开发调试用，生产由后端直接托管 dist | 否 |

机器人链路走 Modbus TCP（`192.168.1.12:502`），配置项在 `config/robot.yaml` 的 `modbus` 段。

---

## 2. 安装部署步骤

```bat
:: 1) 后端依赖 （首次）
cd backend
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

:: 2) 前端依赖 + 构建 （首次 / 改了前端代码）
cd frontend
npm install
node node_modules/vite/bin/vite.js build

:: 3) 配置口令（必做！）
::    复制 .env.example 为 .env，至少设置 EFORT_ADMIN_PASSWORD

:: 4) 启动
::    回到项目根目录，双击 run.bat，或按需分别启动 scripts/start_*.bat
```

> **构建提示**：务必直接 `node node_modules/vite/bin/vite.js build`。
> 经 `npm run build` 在本项目数据量下会 OOM 崩溃（无法 executing）。
> `npm run build` 本身已前置 `tools/check_imports.mjs` 静态导入守卫，直接跑 vite 时
> 建议先手动执行一次守卫，见第 8 节。

数据库无需手工建表：后端启动时 `init_db()` 自动建库建表，位置 `data/robot.db`。

## 3. 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `EFORT_ADMIN_PASSWORD` | 随机临时口令 | **必须设置**。否则每次启动随机生成、只打印在控制台，重启即变 |
| `EFORT_OPERATOR_PASSWORD` | 未启用 | 操作员口令；只能操控机器人，改不了配置 |
| `EFORT_CONTROL_TTL` | `1800` | 控制令牌有效期（秒） |
| `EFORT_SIMULATE` | `auto` | `auto/always/never`，决定是否回退模拟轨迹 |
| `EFORT_REAL_MOTION` | `0` | 真实下发生效需 **同时** 满足它=1 且配置的 `motion.real_write=true` |
| `EFORT_DB_URL` | `data/robot.db` | 可指向独立磁盘/网络盘便于备份 |

`.env` 放在**项目根目录**，后端启动时自动读取；已存在的系统环境变量优先、不被覆盖。

## 5. 安全加固清单（上线前逐条确认）

1. **[必做]** 设置强管理员口令，并定期更换；不要把 `.env` 提交进代码仓库。
2. **[必做]** 开真实下发前确认**双闸**取值：环境变量 `EFORT_REAL_MOTION=1` +
   `config/robot.yaml` → `motion.real_write: true`（两者缺一即安全模拟）。
   写路径已按 `docs/控制器Modbus寄存器勘察报告.md`（2026-09-23 实测）实现：
   `40101` 指令字 / `40103` 速度 / `40135` 点动触发位 / `40139~44` 目标角。
   ⚠ 早期假设 `write_base_addr=30` / `write_speed_addr` / `estop_addr` **已实测证伪并废弃**
   （robot.yaml 中标注「已证伪」），不要再按它们改配置。
3. **[建议]** 打开围栏互锁严格模式：`motion.require_live_safety = true`。
   开启后若前端未实时上报围栏状态（例如用脚本直连 API），所有下发都会被拒。
4. **[建议]** 后端端口不要直接暴露到公网；需要远程访问时走内网 VPN 或反向代理加鉴权。
5. **[必做]** 急停按钮要保持物理可达 —— 软件的急停只是辅助，硬件急停不能被替代。
6. 定期用第 6 节的方法做配置备份与数据库归档，并留存审计事件导出件。

## 6. 备份与恢复

### 6.1 系统配置包（推荐）
- 导出：**运维审计 → 系统配置包 → 导出备份**，拿到 `efort-system/v1` 的 JSON，
  内含安全围栏配置 + 全部点位 + 全部程序（程序条目额外带 `point_name`，导入时自动重新对位点位 id）。
- 导入：同页面 **导入备份**。始终是**安全合并**（按名称去重更新，不删既有数据）。
- 需要网络备份时，直接 `curl http://127.0.0.1:8000/api/system/export -H "X-Control-Token: ..."`。

### 6.2 围栏配置版本化
每次保存/重置/导入围栏配置前，系统自动把**改动前**的配置归档（`safety_config_versions` 表，保留最近 30 条）。
在运维页可直接查看历史版本内容并**一键回滚**（回滚前当前配置会再归档一次，可来回切）。

### 6.3 数据库
停机后整目录复制 `data/robot.db`（连同 `-wal` / `-shm`）即可；历史姿态、录制、点位、审计事件都在里面。

## 7. 健康检查与排障

| 端点 | 用途 |
|---|---|
| `GET /healthz` | 存活探针（不依赖 DB/机器人） |
| `GET /api/version` | 版本号，确认是否为 `0.3.0` |
| `GET /api/system/health` | **健康总览**：服务/db/机器人链路/执行引擎/WS 客户端数/互锁是否生效 |
| `GET /api/safety/live` | 围栏互锁是否有效（`reported/fresh`） |
| `GET /api/events?level=warn&hours=24` | 最近告警，排查首选 |
| `GET /docs` | Swagger，可直接调接口复现问题 |

常见故障：

| 现象 | 原因 / 处理 |
|---|---|
| 页面一直显示模拟轨迹 | 机器人未上电或网线不在机器人侧；`.env` 的 `EFORT_SIMULATE` 是否为 `always` |
| 提示"已交货却没有新版本的画面" | 浏览器缓存。生产静态资源已设 `no-store`，仍异常则强制刷新或清缓存 |
| 改围栏配置保存失败，弹出登录框 | 阶段 4 起保存需管理员令牌；用管理员口令请求控制后重试 |
| 下发被拒，提示"围栏互锁" | 围栏处于 `danger/hit`，或前端未上报状态且开了严格模式 |
| 健康检查 `status=down` | 数据库不可写，看 `db.error` 字段与磁盘空间 |
| 后端起不来 | 看 `logs/app.log` / `logs/uvicorn.log`；确认端口 8000 未被占用 |

## 8. 回归验证（改动后必跑）

```bat
:: 后端测试（沙箱环境需加 --basetemp，避免清 TEMP 干扰退出码）
cd backend
.venv\Scripts\python.exe -m pytest tests -q --basetemp=".pytest_tmp" -p no:cacheprovider

:: 前端：静态导入守卫（防止"用了别的模块的常量却没 import"潜到线上）
cd frontend
node tools/check_imports.mjs
node node_modules/vite/bin/vite.js build
```

守卫的作用：跨模块常量漏 import 在 vite 构建期不报错、headless 全绿，只有浏览器里才炸
`ReferenceError`，靠人工 review 很容易漏——因此每次改动都先跑它。

## 9. 目录速查

```
backend/      FastAPI 服务（core 配置/异常/中间件 · api 路由 · services 业务 · db 模型与 CRUD）
frontend/     Vue3 + Pinia + Three.js（src/three 为 3D 引擎，src/stores 为状态层）
config/       robot.yaml（机器人 DH/限位/连接/真实下发）+ safety.json（安全围栏）
camera/       视觉服务（独立进程，按需启动）
data/         SQLite 数据库（含 WAL）
scripts/      各类启动/自检脚本
logs/         运行日志
```

DH 参数目前仍标记 `calibration_pending`，正式投产前建议按厂家标定数据复核一遍再用于精确定位。
